Method B — CF-Based Fast NII & EVE Computation

Purpose. Method B provides an independent, cash-flow-based approximation of NII and EVE for use in the balance-sheet optimisation pipeline. Unlike Method A (which uses pre-calibrated sensitivity units Δ·NIIunit, exact only at the calibration balance vector), Method B rebuilds NII and EVE from monthly cash-flow schedules and pre-indexed discount factors. This makes it valid for any reallocation of the balance sheet, not just at the current point.

Context. Both methods are benchmarked against the exact IRRBB pipeline (SQL results from irrbb.nii_results / irrbb.eve_results) using the approx_accuracy_report.xlsx produced by accuracy_check.py.

Method B reads from two pre-built .npz files. These are created once by extract_params.py and extract_curves.py before any optimisation run.

Row granularity. Each row i of the n arrays corresponds to one cohort entry: a (product_code, bs_side, currency, start_year, start_month) tuple for cohort products (loans, mortgages, bonds, deposits), or a (product_code, bs_side, currency) tuple for single-row behavioural products (current accounts, saving accounts, equity).

2. How rate_matrix[i, m, s] is Constructed

Built in extract_params.py at pipeline setup time, not at NII runtime. Separate from CurveTensors — all curve lookups happen here, so runtime NII needs no forward-rate computation.

Product typeMonth mScenario sFormula
F — Fixed coupon
(bonds, fixed mortgages, fixed deposits)		 all mall s rate_matrix[i,m,s] = coupon_rate[i]
Constant — no sensitivity to any scenario shift.
V — Floating
(floating loans, floating deposits)		 m < t1

m ≥ t1

ev_t = t1 + k·F   (next fixing event, in months)
fwds(ev_t, F) = F-month forward rate from disc_factors[s]

(products 1100, 2100)		 m ≥ t1each s Monthly lock/float mix:

where lf = fraction still locked in month m, from detailed CF schedule.
Single-row / behavioural
(current accounts, 6000, 8000, …)		 all mall s Zeros — no real monthly profile. These rows fall through to the calibrated fallback (Exception 2).
t1 — months to first fixing. Read from the CF schedule (SQL). If missing and the locked rate is zero, it is derived analytically: t1 = F − (months_since_start mod F). This prevents blanket t1=0 which would overestimate sensitivity by treating all 12 months as floating.

Similarly for renewal_rate_matrix[i,m,s]:

renewal_rate[i, m, s] = clip(a[i] · fwd_1M(m, disc[s]) + b[i], floor[i], cap[i]) where fwd_1M(m, disc) is the 1-month forward rate at month m. (Capital repaid in month m is re-priced at the 1-month spot new-business rate.)

3. NII Computation — Step by Step

Implemented in nii_eve_cf_fast.py, function compute_nii_cf_all.

1Interest NII matrix — _nii_cohort_matrix

NII_int[i, s] = balance[i] · sign[i] · Σ_{m=0..11} interest_yf_m[i,m] · rate_matrix[i,m,s] In vectorised form (single NumPy call): amount_x_out[i,m] = balance[i] · sign[i] · interest_yf_m[i,m] NII_int = einsum("im, ims → is", amount_x_out, rate_matrix)

interest_yf_m[i,m] = outstanding fraction in month m × actual day-count year-fraction of that CF bucket. It is not simply 1/12; it reflects actual days and outstanding profile.

2Renewal NII matrix — _nii_renewal_matrix

NII_ren[i, s] = balance[i] · sign[i] · Σ_{m=0..11} capital_remain_m[i,m] · renewal_rate[i,m,s] capital_remain_m[i,m] = capital_m[i,m] · remain_yf[m] remain_yf[m] = (12 − m − 0.5) / 12 (fraction of horizon left after month m) In vectorised form: NII_ren = einsum("im, ims → is", balance·sign · capital_remain_m, renewal_rate_matrix)

Represents capital repaid in month m (loan runoff, deposit maturity) reinvested at new-business rates for the remaining part of the 12-month horizon.

3Sum and apply exceptions

nii_total[n, n_scen] = NII_int + NII_ren then three in-place corrections (Exceptions 1–3 below)

4. Three Exception Rules

Applied sequentially to nii_total before returning results.

E1 Fixed-rate calibrated override

Problem: F-type products have rate_matrix constant across all scenarios (locked coupon = no delta). This is correct for run-off of an existing fixed cohort. But NMD deposits (product 7060) are modelled as fixed-rate in the CF schedule yet the IRRBB behavioural model assigns non-zero rate sensitivity. Without this fix: 8–10× error for sr_up/sr_dn on 7060.
Detection: max_{m,s} |rate_matrix[i,m,s] − rate_matrix[i,m,base]| < 1e-8 (zero cross-scenario variation) Override for all shocked scenarios s ≠ base: nii_total[i, s] = NII_base[i] + balance[i] · delta_nii_unit[i, s_params] where delta_nii_unit is the calibrated IRRBB sensitivity from the exact pipeline.

E2 Synthetic / behavioural product fallback

Problem: Single-row products (current accounts, savings) and some cohort entries that received a synthetic constant-balance profile (capital_m ≈ 0, outstanding_m ≈ 1.0) have no real CF schedule. Their rate_matrix deltas are invented — not from real repricing.
Detection: (~is_cohort) OR (sum(|capital_m|) < 1e-10 AND max|outstanding_m − 1| < 1e-8) Override for shocked scenarios: nii_total[i, s] = NII_base[i] + balance[i] · delta_nii_unit[i, s_params] Base column is kept from CF computation (preserves base NII level for E3).

E3 Base NII anchoring (bias correction)

Problem: Even a correct rate_matrix will differ from the exact IRRBB pipeline at the base point because of day-count conventions, accrual timing, and gap-based methodology differences. This systematic offset would accumulate as a base error in all shocked scenarios.
bias[i] = balance[i] · nii_unit_rate[i] − nii_total[i, base_idx] ↑ exact calibrated base NII ↑ raw CF-based base NII nii_total[i, :] += bias[i] (applied to ALL scenarios, including base) Effect: NII_base becomes exact by construction. Δ NII = nii_total[i,s] − nii_total[i,base] is unchanged (bias cancels out). All shocked-scenario errors are purely in the delta direction.

5. EVE Computation — Step by Step

Implemented in compute_eve_cf_fast_all / compute_eve_cf_fast_by_product.

1PV matrix via einsum on pre-indexed discount factors

For each cohort i and CF bucket q = 0..cf_n_q[i]-1: PV_frac[i, q, s] = cf_fixed_int_frac[i, q] × cohort_disc_q[i, q, s] Vectorised (mask valid buckets first): cf_masked[i, q] = cf_fixed_int_frac[i, q] × valid[i, q] pv_frac[i, s] = einsum("iq, iqs → is", cf_masked, cohort_disc_q) → shape (n, n_scen) pv_mat[i, s] = pv_frac[i, s] × balance[i] × sign[i]

CF fractions used by product type:

Product typeCF fraction usedRationale
Fixed-rate (F)cf_fixed_int_frac = capital + interest All promised CFs are fixed; PV captures full duration effect.
Floating-rate (V)cf_capital_frac = capital only Floating interest resets to par at each repricing → only capital CFs contribute to duration. Interest CFs wash out in delta (they equal forward rates × discount factor ≈ constant).
Single-row behaviouralzeros (cf_n_q = 0) No maturity schedule; EVE falls back to calibrated eve_pv_factor.

2Delta EVE

eve_base_raw = Σ_i pv_mat[i, base_idx] (raw CF-based base) eve_base = balance · eve_pv_factor (calibrated base — anchored to exact) delta_EVE[s] = Σ_i pv_mat[i, s] − eve_base_raw (shock relative to raw base) Reported as: EVE_base = eve_base (exact calibrated level) delta_EVE[s] as above (CF-based movement)
Override. If eve_pv_frac[i, :, :] is non-zero for a cohort, it replaces cf_fixed_int_frac × cohort_disc_q for that row. This allows scenario-specific PV profiles for products where the standard CF model is insufficient.

7. Residual Errors and Structural Limits of Method B

The remaining failures (flat, sr_up EVE, sr_dn) are not code bugs — they reflect structural approximation limits:

Scenario typeRoot cause of residual error
flat
(long end down, short end unchanged)		 rate_matrix uses F-month forward at a single fixing event ev_t. For non-parallel shocks the forward rate change depends heavily on the tenor chosen. Products with long repricing tenors (F = 12M) pick a forward that does not correctly represent the flat-scenario curve shape. The exact pipeline uses a full term-structure integration; the CF model linearises this.
sr_up / sr_dn
(short-rate only ±25 bp)		 Short-rate shock affects only the front end of the curve (0–12M). Products with t1 > several months miss the shock entirely in the locked period. The exact pipeline prices the gap position precisely; Method B depends on the accuracy of the t1 estimate from SQL, which may be an aggregate approximation rather than the true weighted first repricing date.
par_up / par_dn Parallel shift — all tenors move equally → forward rate approximation is exact regardless of which tenor is chosen. Near-zero errors. ✓
Implication for optimisation. When using Method B in the optimiser hot path, non-parallel shock sensitivities carry a ±1–2% error. For the regulatory EBA SOT this is acceptable (capital buffers dwarf 2% NII/EVE misestimation), but portfolio-level constraints should be set with a safety margin of at least 3–5% relative to the threshold.

8. Why Method B Exists at All (when Method A is more accurate)

Method A is always exact at the calibration point. Why use Method B?

PropertyMethod A (calibrated sensi)Method B (CF-based)
Accuracy at calibration balance Exact by construction ~0–2% error
Validity away from calibration point Linear extrapolation only
(delta_nii_unit fixed at calibration weights)		 Recomputes from actual CF schedule — valid for any weight vector
Captures floor/cap non-linearity No — linear sensi ignores clipping Yes — rate_matrix applies clip() per month per scenario
Captures repricing schedule changes No — t1, F embedded at calibration Partially — t1, F per cohort, though not per-contract
Runtime speed Single dot product — nanoseconds Two einsums — ~0.1 ms for n < 2000

In the optimisation loop the balance vector changes every iteration. Method A gives a first-order estimate of the shifted NII/EVE but cannot capture non-linearities in the rate schedule. Method B acts as an independent cross-check and, for large rebalancings, a more reliable constraint evaluator.
